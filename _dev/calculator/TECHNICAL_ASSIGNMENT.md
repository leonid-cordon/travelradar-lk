# Cancun Calculator Technical Assignment

Статус: расширенное ТЗ для реализации
Дата фиксации: 2026-04-07
Проект: Travel Radar LK
Контекст: первая production-версия премиального travel budget calculator для страницы Канкуна с заделом на дальнейшее масштабирование

## 1. Цель документа

Этот документ фиксирует техническое задание на реализацию следующей сильной версии калькулятора бюджета для Канкуна.

Задача документа:

- перевести продуктовые идеи в конкретные кодовые задачи;
- определить структуру данных и рендер-логики;
- зафиксировать, что именно делаем в первой серьезной версии;
- не потерять фундамент для будущего выноса в отдельный универсальный калькулятор.

## 2. Основная цель калькулятора

Калькулятор должен отвечать пользователю на 4 вопроса:

1. Сколько ориентировочно стоит поездка.
2. Что реально доступно в рамках его бюджета.
3. Почему цена получилась именно такой.
4. Что можно изменить, чтобы уложиться в бюджет.

## 3. Бизнес-цель

Калькулятор должен:

- повышать доверие к статье;
- помогать пользователю дойти до следующего шага;
- вести в каталог или на карточки отелей;
- быть пригодным для повторного использования на других travel-страницах.

## 4. Объем текущей реализации

Текущая реализация относится только к Канкуну.

Сейчас:

- не показываем выбор страны;
- не показываем выбор города;
- считаем только сценарии для Канкуна;
- допускаем прямые ссылки на Booking без affiliate-механики;
- сохраняем в архитектуре задел на будущий переход к universal calculator.

## 5. Ограничения и допущения

- Основной файл реализации на текущем этапе: `ru/content/cancun-budget-2026.html`
- Внешние CSS-файлы можно не трогать.
- Если нужны стили, допустим inline CSS в текущем HTML.
- Дата “сегодня” берется локально в браузере.
- Курс `USD -> EUR` на первом этапе допускается:
  - либо вручную заданным в конфиге;
  - либо обновляемым отдельно позже.
- Прямые Booking-ссылки допустимы как временное решение.

## 6. Non-goals текущего этапа

На этом этапе не делаем:

- отдельную общую страницу калькулятора;
- выбор нескольких стран и городов в UI;
- полноценную affiliate-прокладку;
- серверную синхронизацию цен;
- интеграцию с реальным API авиабилетов или отелей;
- кастомный сложный календарь вместо нативного date picker.

## 7. UX-цель

Калькулятор должен выглядеть как дорогой, уверенный инструмент.

Пользователь должен быстро понять:

- что заполнить;
- какой результат для него главный;
- укладывается ли он в бюджет;
- что делать дальше.

На мобильном калькулятор должен быть так же удобен, как на десктопе.

## 8. Целевой UX-флоу

### 8.1 Пользователь вводит

- откуда летит;
- дату поездки;
- количество ночей;
- количество человек;
- свой бюджет;
- формат отдыха;
- район;
- при желании включает дополнительные расходы.

### 8.2 Калькулятор автоматически считает

- сколько дней осталось до поездки;
- какой это сезон;
- сколько номеров нужно;
- диапазон общей стоимости;
- текущий статус бюджета;
- какие сценарии реально доступны;
- какие конкретные изменения дадут экономию.

### 8.3 Пользователь видит

- диапазон цен;
- ориентир в EUR;
- статус бюджета;
- объяснение, почему цена такая;
- реальные альтернативы;
- подборку отелей;
- CTA-кнопку на следующий шаг.

## 9. Обязательные блоки интерфейса

### 9.1 Верхний инфоблок

Обязательные элементы:

- чип с сегодняшней датой;
- чип с курсом `1 USD ≈ X EUR`;
- короткая подпись, что расчет ориентировочный.

Пример:

- `Сегодня: 7 апреля 2026`
- `1 USD ≈ 0.92 EUR`
- `Цены ориентировочные и зависят от спроса`

### 9.2 Основные поля

Порядок полей:

1. Откуда летите
2. Дата поездки
3. Количество ночей
4. Количество человек
5. Ваш бюджет
6. Формат отдыха
7. Район

### 9.3 Дополнительные расходы

Блок в свернутом виде:

- нужен багаж;
- нужна страховка;
- нужен трансфер;
- учитывать resort fee;
- нужен интернет / eSIM.

### 9.4 Главный результат

Показываем:

- `Минимум`
- `Реалистично`
- `В высокий спрос`

Главная цифра визуально выделена как “реалистично”.

### 9.5 Статус бюджета

В виде премиального бейджа + короткого пояснения:

- `С запасом`
- `Впритык`
- `Выше бюджета`
- `Нужно больше бюджета`

### 9.6 Блок “Что реально доступно”

Показываем 1-3 сценария:

- формат;
- район;
- примерная стоимость;
- сколько номеров заложено;
- небольшой комментарий.

### 9.7 Блок “Как уложиться в бюджет”

Показываем 2-4 подсказки с цифрами экономии.

### 9.8 Блок “Почему такая цена”

Нужен отдельный callout-блок с яркой вертикальной полосой слева.

Внутри коротко объясняется:

- откуда летит пользователь;
- сколько дней до поездки;
- какой сезон;
- сколько номеров заложено;
- какие факторы сильнее всего повлияли на цену.

### 9.9 Блок отелей

Показываем:

- 3 карточки подходящих отелей;
- главную CTA-кнопку;
- вторичную кнопку на статью / сравнение / подборку.

## 10. Требования к визуалу

- Премиальная, спокойная, уверенная подача.
- Не допускать ощущения “калькулятора-таблицы”.
- Главный результат должен читаться за 1 секунду.
- Важные статусы через карточки, чипы, callout-блоки.
- Визуальный ритм: крупные смысловые блоки, затем вторичные пояснения.
- Дополнительные опции не должны перегружать первый экран.

## 11. Mobile-first требования

- Одна колонка на телефоне.
- Нативный date input.
- Крупные tappable элементы.
- Tooltips должны работать по tap.
- Длинные explanatory blocks не должны ломать вертикальный ритм.

## 12. Архитектурная цель

Даже если все пока живет в одном HTML-файле, код должен быть организован как:

- конфиг направления;
- справочники данных;
- pricing engine;
- recommendation engine;
- render layer;
- helper layer.

## 15. Логика вычислений

## 15.1 Derive travel context

Нужна функция вида:

```js
function getTravelContext(selectedDate)
```

Она должна вернуть:

- `today`
- `departureDate`
- `daysUntilDeparture`
- `monthIndex`
- `seasonKey`
- `leadTimeBucket`
- `monthPart`
- `confidenceLevel`

## 15.2 Room calculation

Стартовое правило:

- 1 человек -> 1 номер
- 2 человека -> 1 номер
- 3-4 человека -> 2 номера
- 5-6 человек -> 3 номера
- 7-8 человек -> 4 номера

Формула:

```js
rooms = Math.ceil(people / 2)
```

## 15.3 Flight pricing

Расчет:

```js
flightBase = originConfig[origin].baseFlight
flightReal = flightBase * people * season.flight * leadTime.flight * monthPart.flight
```

Для диапазона:

- `min`: real x 0.92
- `real`: real
- `max`: real x 1.12

Коэффициенты могут быть позже откалиброваны.

## 15.4 Hotel pricing

Расчет:

```js
hotelBase = format.hotelBasePerNight
hotelReal = hotelBase * zone.multiplier * season.hotel * leadTime.hotel * monthPart.hotel * nights * rooms
```

Для диапазона:

- `min`: real x 0.95
- `real`: real
- `max`: real x 1.10

## 15.5 Daily costs

Расчет:

```js
dailyBase = (food + transport + activities + hidden)
dailyReal = dailyBase * season.daily * nights * people
```

Для диапазона:

- `min`: real x 0.93
- `real`: real
- `max`: real x 1.08

## 15.6 Extra costs

Extras рассчитываются отдельно по типу:

- `per_person_roundtrip`
- `per_person_trip`
- `per_booking_trip`
- `per_night_per_room`

## 15.7 Compose range

Итоговый диапазон:

```js
totalMin = flightMin + hotelMin + dailyMin + extrasMin
totalReal = flightReal + hotelReal + dailyReal + extrasReal
totalMax = flightMax + hotelMax + dailyMax + extrasMax
```

Дальше округление:

- до ближайших `$50` или `$100`

Рекомендация:

- `min/max` до `$50`
- `realistic` до `$100`

## 16. Логика бюджетного статуса

Сравниваем бюджет пользователя с `totalReal` и `totalMax`.

### 16.1 Status logic

- `С запасом`: budget >= totalReal + 700
- `Впритык`: budget >= totalReal и budget < totalReal + 700
- `Выше бюджета`: budget < totalReal, но budget >= totalMin
- `Нужно больше бюджета`: budget < totalMin

## 17. Логика блока “Что реально доступно”

Нужно построить несколько альтернативных сценариев:

- все форматы;
- все зоны;
- те же дата, origin, nights, people;
- extras можно сохранить как пользовательские.

Для каждого сценария считаем диапазон и ранжируем.

Правило вывода:

- если текущий сценарий укладывается, показываем его как основной и 1-2 альтернативы;
- если текущий сценарий не укладывается, показываем ближайшие реальные альтернативы;
- если даже минимум не укладывается, показываем самый доступный сценарий.

## 18. Логика блока “Как уложиться в бюджет”

Нужен генератор подсказок.

Минимальный набор советов:

- уменьшить количество ночей на 1;
- уменьшить количество ночей на 2;
- перейти в другой район;
- перейти в более дешевый формат;
- отключить часть дополнительных расходов;
- выбрать менее дорогой период, если поездка попадает в high season;
- если дата очень близкая, подсказать, что раннее бронирование обычно дешевле.

Каждый совет должен показывать:

- действие;
- ориентировочную экономию.

Пример:

- `Минус 2 ночи: экономия около $380`
- `Перейти в Downtown: экономия около $520`
- `Сменить формат на бюджетный: экономия около $940`

## 19. Логика блока “Почему такая цена”

Нужен короткий, понятный explanatory text.

Шаблон:

1. Откуда летит пользователь.
2. Сколько дней до поездки.
3. В какой сезон попадает дата.
4. Сколько номеров заложено.
5. Какие главные ценовые факторы.

Пример генерации текста:

`Вы летите из Европы. До поездки осталось 26 дней, поэтому билеты обычно выше средней цены. Дата попадает в высокий сезон для Канкуна. Для 4 человек расчет проживания идет на 2 номера, поэтому отель заметно влияет на бюджет.`

## 20. Курс USD -> EUR

### 20.1 На первом этапе

Допустим фиксированный rate в конфиге.

### 20.2 Техническое требование

Рендерить:

- курс;
- дату обновления;
- подпись `ориентировочно`.

Пример:

`1 USD ≈ 0.92 EUR`
`Ориентир на 7 апреля 2026`

## 22. Логика выбора отелей

На первом этапе:

- фильтровать отели по `format` и `zone`;
- если список пуст, fallback на более общий сценарий;
- выводить 3 карточки;
- CTA-кнопка ведет на общий список.

Текущая временная модель ссылок:

- отели могут вести на прямой Booking;
- later-compatible структура хранит отдельные поля под будущие affiliate-URL.

## 23. Формат ссылок

Для будущего масштаба сейчас желательно уже различать:

- `directUrl`
- `futureAffiliateUrl`
- `internalUrl`

В первой версии допустимо использовать `directUrl`.

## 24. Рендер-слой

Рендер лучше строить через DOM, а не через слепое `innerHTML` для всех больших блоков.

Нужно отдельными функциями рендерить:

- диапазон цен;
- бюджетные статусы;
- сценарии;
- подсказки экономии;
- объяснение цены;
- карточки отелей.

## 25. Localization-ready требования

Даже если сейчас делаем русский экран, нужно закладывать, что:

- RU/EN/UA версии будут жить отдельно;
- тексты не должны быть размазаны по логике без структуры;
- базовые UI-строки лучше собирать в одном словаре.

Минимум:

- подписи полей;
- статусы;
- пояснения;
- tooltips;

## 28. Acceptance criteria

Версия считается готовой, если:

- пользователь может выбрать дату поездки;
- калькулятор считает daysUntilDeparture;
- итог показывается диапазоном, а не одной цифрой;
- бюджетный статус корректно меняется;
- 4 человека дают расчет минимум на 2 номера;
- дополнительные расходы реально меняют цифру;
- есть персональные советы по экономии;
- есть отдельный explain-block;
- карточки отелей не пустые;
- CTA работает;
- мобильная версия не ломается;
- визуально калькулятор выглядит как качественный premium-block.
