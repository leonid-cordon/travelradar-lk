# Cancun Calculator Specification

Статус: рабочая спецификация по итогам обсуждения
Дата фиксации: 2026-04-07
Проект: Travel Radar LK

## 1. Контекст

Сейчас калькулятор создается для страницы Канкуна и должен работать как сильный, премиальный, понятный пользователю инструмент прямо внутри статьи.

При этом архитектурно он должен быть заложен так, чтобы позже его можно было:

- вынести на отдельную страницу;
- сделать универсальным для других направлений;
- подключать к разным городам и странам через конфиг данных.

На текущем этапе в интерфейсе не показываются поля `страна` и `город`, но в логике и структуре данных должен быть задел под это расширение.

## 2. Главная задача калькулятора

Калькулятор должен отвечать не только на вопрос `сколько стоит поездка`, но и на вопрос:

- что мне реально доступно в мой бюджет;
- почему получается именно такая цена;
- как уложиться в бюджет, если текущий сценарий дороже;
- какие отели и варианты мне смотреть дальше.

## 3. Продуктовые принципы

- Калькулятор должен быть понятным людям ниже среднего уровня подготовки, а не только опытным путешественникам.
- Интерфейс должен быть визуально премиальным, аккуратным и современным.
- Пользователь не должен видеть фальшивую точность.
- Лучше честный диапазон цен, чем одна “магическая” цифра.
- Калькулятор должен объяснять логику расчета простым языком.
- Mobile-first обязателен.

## 4. Текущий охват

Направление: Канкун, Мексика

Аудитория вылета:

- Канада

## 5. Что вводит пользователь

Основные поля:

- Откуда летите
- Дата поездки / дата вылета
- Количество ночей
- Количество человек
- Ваш бюджет
- Формат отдыха
- Район проживания

Дополнительный блок:

- Багаж
- Страховка
- Трансфер из аэропорта
- Resort fee
- Интернет / eSIM

Дополнительные траты лучше показывать в свернутом блоке, чтобы не перегружать первый экран.

## 6. Что считается автоматически

- Сегодняшняя дата берется локально в браузере.
- По дате поездки считается число дней до вылета.
- Из даты автоматически определяются:
  - месяц;
  - сезон;
  - близость поездки;
  - первая или вторая половина месяца, если это нужно для коэффициентов.
- Количество номеров считается автоматически.

Базовое правило для первой версии:

- `rooms = ceil(people / 2)`

## 7. Модель расчета

### 7.1 Перелет

Формула:

- базовая цена по origin;
- коэффициент сезона;
- коэффициент срока до поездки;
- при необходимости коэффициент первой/второй половины месяца.

### 7.2 Отель

Формула:

- базовая цена по формату;
- коэффициент района;
- коэффициент сезона;
- количество ночей;
- количество номеров.

### 7.3 Прочие расходы

Считаются на человека в день:

- еда;
- транспорт;
- активности;
- скрытые бытовые траты.

### 7.4 Дополнительные расходы

Добавляются отдельно, в зависимости от типа:

- фиксированно;
- на человека;
- на ночь;
- на бронирование.

## 8. Как показывается результат

Итог должен показываться не одной цифрой, а диапазоном:

- минимум;
- реалистично;
- верхняя граница / пиковый спрос.

Пример логики вывода:

- От: `$4,600`
- Реалистично: `$4,900`
- До: `$5,300`

Рядом вторым слоем:

- примерный пересчет в `EUR`

## 9. Статус бюджета

Калькулятор должен показывать один из статусов:

- С запасом
- Впритык
- Выше бюджета
- Нужно больше бюджета

Под статусом должен быть короткий, человеческий комментарий.

## 10. Блок рекомендаций

Обязательные блоки результата:

- Что реально доступно за ваш бюджет
- Как уложиться в бюджет
- Почему такая цена
- Подходящие отели

### 10.1 Что реально доступно

Калькулятор должен показывать 1-3 сценария, которые реально подходят под введенный бюджет.

### 10.2 Как уложиться в бюджет

Советы должны быть персональными и численными.

Примеры:

- Минус 2 ночи: экономия около `$...`
- Перейти из center в downtown: экономия около `$...`
- Сменить формат с comfort на budget: экономия около `$...`
- Сдвинуть поездку на менее дорогой период

### 10.3 Почему такая цена

Нужен отдельный блок-пояснение с вертикальной акцентной полосой слева.

Этот блок должен кратко объяснять:

- откуда летит пользователь;
- сколько дней осталось до поездки;
- влияет ли сезон;
- сколько номеров заложено;
- какие основные факторы дали такую цену.

## 11. Отели и ссылки

Сейчас допустимы прямые реальные ссылки на Booking, если affiliate-подключение еще не готово.

Но фундамент должен быть заложен уже сейчас:

- ссылки на отели хранятся централизованно;
- в логике предполагается, что позже можно будет заменить прямые Booking URL на affiliate-ready слой;
- UI не должен зависеть от того, Booking это, local page или redirect.

Рекомендуемая модель данных отеля:

- `slug`
- `name`
- `city`
- `zone`
- `formats`
- `priceMin`
- `priceMax`
- `directUrl`
- `futureAffiliateUrl`
- `hasLocalPage`
- `isActive`

## 12. Валюты

Основа расчета:

- USD

Дополнительный ориентир:

- EUR

Дополнительно можно показывать:

- `1 USD ≈ X EUR`
- дата обновления курса

Курс лучше оформлять как аккуратный информационный чип в верхней части калькулятора.

## 13. Термины и подсказки

Для терминов нужны понятные tooltip / helper-пояснения:

- Resort fee
- eSIM
- Страховка
- Багаж
- Трансфер

Логика:

- hover на desktop;
- tap / click на mobile.

## 14. Визуальные требования

- Калькулятор не должен выглядеть как бухгалтерская форма.
- Нужен premium feel.
- Хороший ритм, воздух, карточки, статусы, аккуратные подписи.
- Основной результат должен визуально доминировать.
- Вторичные настройки должны быть деликатно спрятаны.

## 15. Mobile-first требования

- Нативный date picker
- Одна колонка на мобильных
- Крупные поля
- Минимум мелких интерактивных зон
- Tooltips и пояснения должны работать на touch

## 16. Архитектурный задел на будущее

Будущая целевая модель:

- один движок калькулятора;
- разные конфиги направлений;
- отдельная общая страница калькулятора;
- встроенные версии калькулятора на страницах статей.

Текущий калькулятор Канкуна должен быть первым конфигом этой системы.

## 17. Зафиксированные решения на текущий момент

- Пока делаем Канкун-версию.
- Страна и город пока не выводятся в UI.
- Сейчас допустимы прямые Booking-ссылки без affiliate.
- Позже должен быть переход на партнерскую схему без поломки интерфейса.
- Внешний CSS пока не обязателен: допустим inline CSS в текущем файле, если это нужно для качества.
